## 1. 한 줄 정의

**"AI와 함께 만드는 나의 첫 프로그램"**
남이 만든 앱을 쓰는 사람에서, 내 앱을 직접 만드는 사람으로.

같은 스타터킷 프로젝트에서 출발하지만, ChatGPT와 대화하며 이름·디자인·기능을 바꿔가는 동안 팀마다 완전히 다른 결과물이 나온다. (포스터 예시: 같은 구조의 "말씀로그" / "워터팡")

## 3. 목표 (Goal)

School Track(4주 코딩 개념 커리큘럼)과 달리, Church Track은 **신앙 커리큘럼이 아니다.** 오히려 난이도는 더 높은 방향:

- 자신이 만든 Starter Kit을 팀 단위로 ChatGPT를 이용해 수정
- 팀이 스스로 정의한 문제를 해결하는 웹 서비스를 완성
- 결과물은 "내가 만든 것"이라고 말할 수 있는 나만의 앱

즉 목표는 **개념 이해(School Track)** 가 아니라 **완성된 산출물 제작 경험(Church Track)** 에 가깝다.

## 4. 세션 구성 (Session Structure)

**필수 과정**: 4 Section (1 Section = 1.5시간)
- Day 1 (7/28): Section 1 + Section 2
- Day 2 (7/29): Section 3 + Section 4

**확장 가능성 (별도 검토 필요, 이번 Scope 제외)**
- 2시간 × 4회 추가 커리큘럼 — 별도 연장선 구성 필요, 이번 Mission Scope 밖

### Section 후보 (확정 아님 — 다음 Mission에서 구체화)

| Section | 후보 주제 | 비고 |
|---|---|---|
| Day1-①| 팀 빌딩 + 문제 정의 (기획) | 어떤 문제를 풀지 팀별로 정의 |
| Day1-②| 아이디어 구체화 + 디자인 | Starter Kit 골격 확인, 화면/기능 스케치 |
| Day2-①| AI와 개발 (커스터마이징) | ChatGPT로 Starter Kit 수정 |
| Day2-②| 프로젝트 마무리 → 발표 준비 → 팀 발표 → 피드백 → 클로징 | 별도 발표 준비일 없이 Section 4 안에서 전부 진행 (7번 참고) |

## 5. 톤 & 프로세스 (Tone & Process)

School Track보다 훨씬 **실무형/프로덕트형** 톤:

- 실생활 문제를 해결하는 서비스를 기획 → 실제 IT 프로덕트 프로세스(기획 - 디자인 - 개발 - 테스트/QA)를 그대로 체험
- 팀원들과 함께 문제를 **정의하고 - 발견하고 - 해결하는** 팀워크 중심
- 신앙 색채는 넣지 않되, "문제를 발견하고 해결하려는 마음"을 크리스천이 가져야 할 태도의 톤으로 자연스럽게 녹임 (설교 X, 은유적 톤)

---

## 6. School Track과의 차이

| 구분 | School Track | Church Track |
|---|---|---|
| 목표 | 알고리즘/코딩 개념 이해 | AI로 실제 작동하는 웹 서비스 완성 |
| 톤 | 학교 수업, 개념 중심 | 실무 프로덕트 프로세스 체험 |
| 산출물 | 미니 프로젝트 발표 (플로우차트 수준) | 실제 작동하는 웹 서비스 + 발표회 |
| 신앙 요소 | 없음 | 없음 (단, 태도/톤에 은유적으로 반영) |
| 참여 구조 | 학생 단독 | 중고생 주도 + 초등학생 팀원 + (유동) 학부모 |

## 7. 최종 발표회 — Discovery Showcase (확정, 2026-07-19)

이름: **Discovery Showcase**. 심사·순위·시상 **없음** — "심사"가 아니라 "공유와 축하" 중심. 별도의 날이 아니라 **Session 4(마지막 Section) 안에서 전부 진행**: 프로젝트 마무리 → 발표 준비 → 아래 5단계.

**① 부스 운영**
- 팀별로 부스를 하나씩 맡는다. 노트북에 자기 팀 웹 프로젝트를 실행해 둔 채로 대기.

**② 발표**
- 팀마다 짧게 소개: 어떤 문제를 해결했는가 / 왜 만들었는가 / 어려웠던 점 / 재미있었던 점
- 팀당 발표 시간: **약 3~5분**, 길게 끌지 않음

**③ Expo (자유 관람)**
- 발표가 끝나면 학생들이 자유롭게 다른 팀 부스를 돌아다니며 직접 체험 + 질문 + 대화

**④ Post-it Feedback**
- 각 작품 옆에 포스트잇을 붙일 수 있게 준비
- 예시 문구: 💡 좋은 아이디어였어요! / 👏 디자인이 멋졌어요! / 🔥 이 기능이 가장 재미있었어요! / 🤔 이 기능도 있으면 좋겠어요!
- 학생들은 여러 작품에 자유롭게 포스트잇을 남긴다

**⑤ 마무리**
- 각 팀이 자기 작품에 붙은 포스트잇을 읽는다
- 서로 감사 인사를 나누고 프로그램을 마무리

**평가/피드백 톤**
- School Track에서 쓴 "I like...", "I learned...", "My favorite part..." 같은 긍정적 피드백 언어와 같은 결

**여전히 TBD**
- 전체 발표회 진행 시간(부스 준비 + 발표 + Expo + 마무리 합산 소요 시간), 사회자 유무, 발표 순서 결정 방식(추첨/자유)
- 참관 대상 (학생만 / 학부모 / 교회 성도 / 온라인 공유)
- 부스/포스트잇 준비물 (부스 배치, 포스트잇·펜 수량, 작품 설명 카드 유무)
- 오프닝, 시상식(없다면 대신 수료증 전달 등), 단체 사진, 다과 같은 앞뒤 순서
- 사진/영상 촬영 및 기록 방식

## 9. Starter Kit 설계 방향 (GPT 컨텍스트 확인, 2026-07-19)

**기술 스택**
- React + Vercel 배포
- 저장은 localStorage (복잡한 Backend 없음)
- 데이터는 JSON 더미 데이터

**Starter 컨셉**: "기록 + 관리 + 챌린지"형 앱
- 기본 기능: 기록 추가/삭제/수정, 통계, 차트, 모바일 반응형
- 학생이 수정하는 요소: 앱 이름, 컬러, 캐릭터, 아이콘, 미션, 그래프 제목/타입, 기준 데이터, 기능 일부
- 하나의 Starter에서 나올 수 있는 예시: Water Challenge, Faith Journey, Study Tracker, Healthy Me, Habit Tracker

**UI 방향**
- "AI가 만든 티" 금지 — Apple Health / Finch / Habit 앱 느낌의 실제 서비스감
- 심플, MZ 감성, 모바일 우선

**핵심 원칙**
- 학생은 "새 프로젝트"를 만드는 게 아니라 "같은 Starter를 수정·확장·브랜딩"하는 형태
- 목표는 "좋은 개발자"가 아니라 "나도 앱을 만들어봤다"는 첫 성공 경험
- 학생 경험 흐름: AI에게 요청 → 디자인 수정 → 기능 수정 → 앱 완성 → 발표

**이 Starter를 실제로 만들 때 Claude Code가 지킬 것** (미리 확인된 지침, 다음 Mission에서 적용)
- 유지보수보다 교육성 우선, 과도한 추상화 금지
- 코드가 조금 길어지더라도 이해하기 쉬운 구조 선호
- 학생이 수정할 부분에는 주석으로 명시
- React 초급자가 읽어도 이해할 수 있는 코드
- 한 파일에 너무 많은 책임을 몰아넣지 않도록 컴포넌트 적절히 분리
